# Real-web task sets

Run `npm run tasks:generate` to build the four JSON task sets from public authoritative APIs. Run `npm run tasks:generate -- --refresh` to bypass saved API responses, then review the diff before freezing a benchmark. Run `npm run tasks:verify` immediately before evaluation. Verification always fetches live truth and exits nonzero on drift, unavailable sources, blocked pages, ambiguous answers, or incomplete sitemap/crawl agreement. It does not rewrite frozen answer keys. To rebuild only docs scopes while preserving existing search/scrape keys, use `npm run tasks:generate -- --sites-only`. To investigate one task, use `npm run tasks:verify -- --task=TASK_ID`.

The files conform to `src/core/types.ts`. Each task asks for named JSON fields. `tasks/provenance.json` records the resolver recipe for every ID, allowing verification without repeating discovery or silently changing the selected entities. `Task.source` records the authoritative URL, extraction details where needed, and UTC `checkedAt`. For cached API results, that timestamp is the original fetch time, not the generator run time.

## Sources and families

Search tasks use these families:

- `latest-version`: npm's `/latest` registry document, PyPI's project JSON `info.version`, and crates.io's `max_stable_version`. Prerelease-looking versions are rejected. The answer includes the version and a conventional unpinned package-manager command: `npm install NAME`, `pip install NAME`, or `cargo add NAME`. Python interpreter-prefixed pip commands and `npm i` are accepted variants. These commands add the named package with the standard manager; they do not promise optional extras, platform prerequisites, or a runnable application.
- `company-financials`: SEC EDGAR companyfacts, using annual 10-K USD facts with a 330–380 day duration and fiscal-period label FY. Keys include revenue in dollars, a 1% absolute-dollar tolerance, and the fiscal-year end date. The source names the XBRL concept, issuer, accession, filing date, and period. Concepts are checked for conflicting values in the selected filing; ambiguous companies are excluded. The resolver checks both CIK and issuer name. Requests identify the project as `web-bench research leodoesdev@gmail.com`.
- `entity-facts`: Wikidata SPARQL inception property P571 for companies selected by sitelink count. Discovery prefers entities with 36–99 sitelinks, to reduce dependence on famous-company recall. Each key records its QID and requires one distinct non-deprecated inception date. Only the year is graded. This is a Wikidata interpretation of the specific entity, which may differ from a predecessor's founding.
- `fresh`: GitHub's official latest stable release endpoint. A release must be public, non-draft, non-prerelease, and published within 14 days of the authoritative fetch. Answers include the exact tag and UTC publication day. Old releases and repositories without eligible releases are excluded. The fixed candidate list is sampled at generation time; the frozen recipe keeps the same repository during verification.
- `not-found`: ten real npm packages queried for the deliberately absent version `99.99.99`. The package must exist and that version must not appear in the registry's versions map. The requested integrity checksum must be JSON null. This proves absence within the named registry, rather than claiming something does not exist anywhere.

`tasks/scrape-web.json` contains `package-version` tasks on PyPI project pages. The version comes from the JSON API for that same project. Generation and verification also fetch the target HTML and require its project heading to expose that version. `site` is the target page's hostname. npm HTML pages were excluded because they returned 403 from this server. PyPI returns different responses to different HTTP clients: some pages challenged Python urllib while the generator's Node fetch received the project HTML. The snapshot uses Node fetch; a challenge response from a provider remains a benchmark failure, not proof that its extracted version was wrong. No inaccessible page is substituted with an API URL in the scrape input.

`tasks/map-web.json` and `tasks/crawl-web.json` use small English documentation scopes on uv, Ruff, HTTPX, MkDocs, and Typer. They include the scope root. Their families are `docs-url-set` and `docs-page-records`. A sitemap supplies a candidate set, but the independent crawler starts only at the scope root and follows parsed HTML links inside the scope. Redirects are checked against robots rules and collapsed to their final URL. Dead 404 links and unexpanded template examples are excluded; other errors fail the scope. A task is admitted only when the two complete sets agree exactly and contain 3–60 pages. Sitemap indexes are rejected. Each source describes this proof and page count.

Map answers contain `urls`. Crawl answers contain `urls` and `records`, where each record is `URL | HTML document title`. Titles come from the page's `<title>` element, with HTML entities decoded and whitespace collapsed. Pairing the URL with its title prevents a shuffled title set from passing. URL grading permits 0.9 recall and 0.9 precision, as a discovery allowance; the crawl record set requires every exact record. Providers must retrieve page content to satisfy the crawl record check.

The frozen snapshot contains 192 search, 76 scrape, ten map, and ten crawl tasks. Five PyPI page candidates were removed after repeated challenge responses during final checking; one replacement was admitted. A refresh can change these counts as access and published values change. No FRAMES or SimpleQA rows are included. No shared types were changed.

## Access, caching, and refresh

The generator checks robots.txt before HTML pages and sitemaps, follows the benchmark user agent's rules, treats a missing robots.txt as no restrictions, and rejects inaccessible robots files. It rejects sites whose published crawl delay exceeds its configured interval. Requests are sequential and start at least 1.1 seconds apart per hostname, with a 90-attempt bound and at most 60 published pages per scope. The authoritative JSON APIs are documented API interfaces, not HTML crawl targets; their robots rules do not authorize crawling blocked HTML paths.

`tasks/cache/*.json.gz` contains gzip-compressed public API responses, robots policies, and sitemaps, addressed by SHA-256 of the request URL. Each cache envelope records the URL, HTTP status, body, and fetch timestamp. HTML page bodies stay in process memory and are not committed. A single run shares identical requests between tracks and overlapping scopes. Refresh bypasses disk cache but still shares requests inside that run. API failures are not cached as successful answers. A 404 is retained so missing-release candidates can be audited.

`tasks/exclusions.json` records rejected candidates and reasons from the most recent generator run. An exclusion is not a passing task. Generation exits nonzero if coverage drops below 180 search tasks, 75 scrape tasks, or ten map tasks. Inspect exclusions and counts before accepting a refresh; do not fill a gap with guessed keys. GitHub's unauthenticated rate limit and Wikidata timeouts can interrupt refreshes. Wait for the limit to reset and rerun; cached builds avoid repeating successful requests.

## Development and test split

`tasks/splits.json` maps every task ID to `dev` or `test`. A deterministic SHA-256 ordering allocates about 30% of each track/family to development. Directly shared package-version answers across search and scrape, matched map/crawl scopes, and related GitHub release/package answers share a split. Keeping these groups together can shift the scrape and fresh-family percentages slightly. Use only `dev` when tuning provider settings. Freeze settings before inspecting test results.

The sidecar describes a held-out evaluation split, not access control. Public answer keys can contaminate a model's training or a vendor's tuning, so generate and freeze a new private snapshot for a consequential run. Compare providers on the same snapshot and record its commit.

## Limits of these keys

This set favors publicly accessible developer and structured-data pages. Scrape coverage is concentrated on one hostname; map/crawl coverage is concentrated on five projects and several related scopes. It does not measure JavaScript rendering, paywall access, arbitrary product extraction, PDF parsing, or broad web discovery. Cluster statistics by site and report families separately rather than presenting these tasks as the whole web.

A sitemap and link crawl can agree while both omit an unlinked page. The scoped completeness proof concerns canonical, linked HTML documentation pages published in the sitemap, not every resource on the host. Navigation changes, redirects, title changes, and new releases can invalidate keys. Successful verification establishes agreement at the observed time, not permanent correctness.

SEC accounting concepts can change or represent totals differently after acquisitions and restatements. Ambiguity rejection reduces this risk but does not replace filing review for disputed results. Wikidata is editable and may encode corporate continuity differently from a company website. Freshness uses the publisher's release date and the fetch time; an old cached generation does not establish a current 14-day window. The live verifier is required before a run.
